# Устройство сетевой части

## Цепочка вызовов

```
приложение  →  apiManager  →  transportService  →  сеть
```

| Уровень | За что отвечает | Файлы |
| --- | --- | --- |
| Приложение | экран и состояния интерфейса | `src/screens/`, `src/hooks/` |
| apiManager | методы по темам, DTO, проверка и преобразование | `src/api/` |
| transportService | общий `fetch`, таймаут, отмена, ошибки и логи | `src/shared/api/` |
| Сеть | HTTPS и удалённый API | `api.worldbank.org/v2` |

Правило простое: **`fetch` вызывается только в `transportService`.** Экраны и хуки обращаются
к `apiManager`, а он — к транспорту. Проверяется поиском по проекту:

```bash
grep -rn "fetch(" src --include=*.ts --include=*.tsx
```

Найдётся одна строка — в `src/shared/api/transportService.ts`.

## Как проходит один запрос

1. `CatalogScreen` вызывает `useCatalog`.
2. Хук вызывает `apiManager.countries.list({ page, region, signal })`.
3. `countriesApi` собирает путь `/country?format=json&page=1&per_page=50`, заводит `requestId`
   и передаёт запрос в `transportService.requestJson`.
4. `transportService` ставит таймер на 10 секунд, связывает внешний `AbortSignal` со своим
   контроллером, пишет `http.start`, делает `fetch`, проверяет `response.ok`, разбирает тело
   и пишет `http.end`.
5. `countriesApi` проверяет форму ответа (`parseCountryPage`) и превращает DTO в `Topic[]`.
6. Хук кладёт результат в состояние, экран перерисовывается.

Транспорт ничего не знает про страны: он возвращает `unknown`. Знание о полях живёт в модуле API.

## DTO и модель приложения

`CountryDto` — то, что приходит от сервера: `iso2Code`, `capitalCity`, вложенные объекты
`region` и `incomeLevel`. `Topic` — то, с чем работает интерфейс: плоские поля, русские названия
региона, готовая ссылка на флаг.

TypeScript проверяет типы при компиляции, но `response.json()` возвращает `unknown`: сервер может
прислать что угодно, и типы об этом не узнают. Поэтому есть `parseCountryDto` — проверка во время
выполнения. Она смотрит каждое поле и при расхождении бросает `contract_error` с именем поля,
например `country.name`.

Приведение `as CountryDto` такой проверкой не является: оно только успокаивает компилятор.

## Коды ошибок

| Код | Когда возникает | Что видит пользователь |
| --- | --- | --- |
| `http_error` | сервер ответил кодом 4xx или 5xx | «Сервер ответил ошибкой 404» |
| `not_found` | ответ 200, но в теле `message` вместо данных | «Такой записи нет в справочнике» |
| `invalid_id` | код страны не прошёл проверку формата до запроса | «Неверный формат кода страны» |
| `network_error` | запрос не дошёл: сеть, DNS, TLS | «Нет связи с сервером» |
| `timeout` | ответа нет дольше 10 секунд | «Сервер не ответил вовремя» |
| `cancel` | условия сменились или экран закрыли | ничего, это штатный ход |
| `parse_error` | тело не разобралось как JSON | «Ответ сервера не удалось разобрать» |
| `contract_error` | JSON разобрался, но поля не те | «Ответ не совпал с ожидаемым форматом» |

Первые семь определяет транспорт, `contract_error` — модуль API. HTTP 404 сетевым отказом
не считается: сервер ответил, связь была.

## Отмена и гонки

Защита двойная.

**Отмена.** У каждого запроса свой `AbortController`. Функция очистки эффекта вызывает `abort()`,
поэтому при смене региона или уходе с экрана запрос прекращается. Отмена не показывается
пользователю как ошибка.

**Счётчик актуальности.** `createRequestGuard` выдаёт номер каждому запросу и умеет сказать,
последний ли он. Ответ применяется только при совпадении номера:

```ts
const token = pageGuard.current.start();
...
.then((result) => {
  if (!pageGuard.current.isCurrent(token)) return;
  setItems(result.items);
});
```

Зачем второй механизм, если есть отмена: `abort()` прекращает запрос, но ответ может уже лететь
обратно, а промис — уже стоять в очереди микрозадач. Проверка номера гарантирует, что поздний
ответ не перезапишет свежие данные. То же относится к `finally`: устаревший запрос не снимает
индикатор загрузки, потому что его уже сняли другие.

## Логи

Логи пишет `src/shared/api/logger.ts`, только при `__DEV__`. На каждый `http.start` приходится
ровно одно завершающее событие.

```json
{"event":"http.start","timestamp":"...","requestId":"req-1","method":"GET","route":"/country"}
{"event":"http.end","timestamp":"...","requestId":"req-1","method":"GET","route":"/country","status":200,"durationMs":229,"outcome":"success"}
```

Ошибка проверки DTO пишется отдельным событием с тем же `requestId`:

```json
{"event":"api.contract_error","timestamp":"...","requestId":"req-1","route":"/country","field":"country.name"}
```

Что даёт каждое поле:

- `requestId` связывает начало и конец, по нему фильтруется одна попытка;
- `route` — безопасная метка маршрута без query, для карточки это `/country/:id`;
- `status` отвечает, ответил ли сервер: `null` значит, что до него не дошли;
- `durationMs` отличает мгновенный отказ от честного ожидания лимита;
- `outcome` — чем кончилось.

В лог не попадают заголовки, cookies, токены, тела ответов, персональные данные и поисковые
строки. Лог собирается из разрешённого списка полей, а не очищается от лишнего.

## Состояния каталога

| Состояние | Что на экране |
| --- | --- |
| `loading` | индикатор, пустой результат не показывается |
| `success` | список карточек |
| `empty` | объяснение и кнопка сброса условий |
| `error` | причина, кнопка «Повторить», кнопка «Показать демо-данные» |
| дозагрузка | список остаётся, внизу отдельный индикатор или ошибка порции |

Ошибка следующей порции не сбрасывает уже загруженные записи. Повтор недоступен, пока идёт
текущий запрос: за этим следит флаг `moreInFlight`.

## Резервный режим

Демо-данные лежат в `src/data/fixtures.ts` и включаются **только вручную**, кнопкой на экране
ошибки. Пока они показаны, вверху висит метка «Демо-данные» и кнопка «Вернуться к сети».

Так сделано намеренно. Если подменять ответ сервера резервными данными молча, пользователь
решит, что видит свежие данные, поломка не всплывёт ни в интерфейсе, ни в логах, и работающее
приложение станет неотличимо от сломанного.
